# Stack research findings (June 2026)

Digest of the 10-agent research workflow (5 researchers + 5 adversarial verifiers) that validated the architecture in SPEC.md. Each area lists the verdict, the concrete recommendation, risks, and the verification status of every load-bearing claim.

Compute replace/widget decorations per-viewport where layout permits and keep block-layout-changing decorations in a StateField, accepting the rebuild cost only on affected lines.

AREA: sync
VERDICT: The layer holds up as designed — build on y-partyserver 2.2.0+ with hibernation enabled — with the caveat that you must bring your own persistence (update-log + compaction into DO SQLite) and must use y-partyserver's matched YProvider client (or replicate its awareness-interval fix in any custom client, including the CLI), or idle connections will wake the DO every 15 seconds and erase the hibernation cost savings.

RECOMMENDATION: Build on y-partyserver >=2.2.0 (cloudflare/partykit) with partyserver >=0.5.6, yjs pinned to one version (13.6.31 as of May 2026), and @cloudflare/workers-types ^4.20260424.1; set static options = { hibernate: true } on the YServer/withYjs class and use y-partyserver's YProvider in the browser (it is the only stock client that keeps the DO hibernating between keystrokes). Do NOT adopt y-durableobjects as the framework (slower maintenance, Hono coupling, awareness-interval fix still unshipped), but DO copy its YTransactionStorageImpl design for persistence: write every incoming Yjs update as its own SQLite row inside the doc 'update' handler (not just debounced onSave), and compact at ~a few hundred KB / few hundred updates by replaying into a Y.Doc and rewriting a single state blob, chunking across 2MB rows or spilling to R2 if the blob approaches the row cap. Implement onLoad() to apply state-blob + pending updates. For edit history, store per-version records of {markdown text, Yjs state vector, encodeStateAsUpdate blob} in SQLite/R2 and diff versions as plain text (which also serves the CLI's pull-base/push-diff flow); derive attribution from the raw update log with a server-maintained clientID-to-user table rather than gc:false + Y.PermanentUserData, since y-partyserver hardcodes gc:true and PermanentUserData is experimental. Hand-rolling on the raw Hibernation API is viable (TimoWilhelm's repo proves the shape) but would re-implement, less battle-tested, exactly what y-partyserver 2.1.0 already fixed; reserve that option only if PartyServer's pre-1.0 churn becomes a problem. Cap docs at low single-digit MB of markdown, treat 32,768 sockets/DO and ~1k msg/s as the platform envelope, and budget costs using hibernation pricing (idle open tabs are free; 20:1 incoming message ratio; outgoing free).

RISKS:
  - Client coupling for hibernation: the cost savings require y-partyserver's own YProvider (which disables the awareness _checkInterval and listens to 'change' not 'update'). Any vanilla y-websocket client — including a future 'ink watch' CLI mode or third-party integrations — will send awareness renewals every ~15s and wake the DO continuously while connected, silently restoring the pre-hibernation cost profile.
  - y-partyserver gives you zero persistence out of the box, and its debounced onSave (2s/10s max) means up to ~10s of edits can be lost on DO crash/eviction if you follow the README pattern naively. Persist every update to DO SQLite in the doc 'update' handler (y-durableobjects-style update log) instead of relying on debounced full-state saves.
  - y-partyserver hardcodes gc:true in WSSharedDoc, and both reference compaction implementations re-encode state through a gc:true Y.Doc — so deleted content is purged from the canonical stored state. If history/attribution is built later on Y.snapshot + PermanentUserData assumptions, it will not work without forking the server class; design history around markdown snapshots + state vectors + a retained raw update log from day one.
  - partyserver is still pre-1.0 (0.5.6) and y-partyserver had three breaking-ish releases in Feb-Apr 2026 (withYjs mixin extraction, ctx.id.name addressing change requiring workers-types ^4.20260424.1, no support for idFromString/newUniqueId addressing). Expect API churn; pin versions and read changelogs on upgrade.
  - Per-row 2MB cap in DO SQLite: a single encodeStateAsUpdate blob for a very large doc (or one with heavy retained history) can exceed 2MB and writes will throw. Chunk the compacted state across rows or spill to R2 above ~1.5MB; also enforce a product-level doc-size ceiling (low single-digit MB of markdown) to stay within the 128MB isolate and keep initial-sync latency sane.
  - Awareness peer-timeout is disabled in the hibernation-safe pattern, so crashed clients (no close frame) can leave ghost cursors until the connection is reaped by the network layer; y-durableobjects users observed more 'Client disconnected' errors. Consider a low-frequency client-side awareness null-out on visibilitychange/unload and server-side cleanup in onClose/onError.
  - The duplicate-yjs-import hazard ('Yjs was already imported' breaks constructor checks and can corrupt CRDT behavior) is easy to hit in a monorepo with the editor (y-codemirror.next), server, and CLI all depending on yjs — enforce a single hoisted yjs version (pnpm overrides/resolutions).
  - One DO per document is single-threaded: every keystroke fans out to N connections, and the soft guidance is ~1,000 req/s per object. Fine for tens of concurrent editors per doc; a viral read-heavy doc (hundreds of live viewers) would need a read-replica/pubsub tier that this architecture does not currently include.

AREA: cli-merge
VERDICT: The design holds — server-side diff(base→new) fuzzy-applied onto current Y.Text is exactly what Obsidian Sync, Relay, and Automerge updateText do in production — with the caveats that the base must be stored as plain text (state-vector reconstruction requires gc:false and is a trap) and a rewrite-ratio guard with per-hunk apply verification is mandatory.

RECOMMENDATION: Build the merge yourself on proven pieces — it's ~200 lines, and every precedent (Obsidian Sync, Relay, Automerge updateText, Loro update) confirms the shape. Concretely: (1) Diff layer: use @sanity/diff-match-patch v3.2+ (maintained, surrogate-pair-safe) — makePatches(base, new) with cleanupSemantic, then applyPatches against the CURRENT Y.Text string with default Match_Threshold; check the per-patch results array and return failed hunks as conflicts instead of dropping them. Then compute the minimal char diff current→mergedResult (fast-myers-diff or dmp) and apply it via Y.Text.applyDelta inside a single Yjs transaction in the Durable Object (never in a stateless Worker), so concurrent-edit positions and anchors are preserved. Keep node-diff3 (v3.2.1, June 2026) as an optional line-level 3-way mode that can emit conflict markers — Relay's exact stack. (2) Pull metadata: do NOT plan on reconstructing base text from a state vector — that requires gc:false (snapshot = SV + delete set) and unbounded doc growth. Instead `ink pull` writes doc.md plus .ink/meta.json {docId, serverVersionId, sha256(baseText)} and .ink/base.md; the server ALSO stores the pulled base content-addressed by hash (cheap — it already has the text at pull time; TTL/LRU evict). `ink push` sends {newText, baseHash}; if the server still has the base it merges server-side, else the CLI uploads base.md from disk. Keep gc:true; implement the separate history feature as periodic full-text/update snapshots, not Y.Snapshot. (3) Rewrite guard: compute changeRatio = levenshtein(base,new)/max(len) (dmp's diff_levenshtein); above ~60% (tunable), reject by default with a clear message and require --force or --strategy=replace; in guard territory, fall back to paragraph/line-level matching (Loro update_by_line precedent) so untouched paragraphs anchor by content; re-anchor comments via the stored text-quote selectors (Hypothesis fuzzy-anchoring algorithm) after any large merge. (4) Auth: use better-auth's official Device Authorization plugin (RFC 8628) for `ink login` — it works headless where Wrangler's localhost:8976 callback fails — plus INK_API_KEY env var for CI/agents; store tokens in the OS credential store when available with a chmod-600 fallback file (gh model); avoid keytar (archived). (5) Distribution: publish a scoped npm package (the name `ink` is taken) runnable via npx, and ship bun build --compile cross-compiled binaries (linux-x64/arm64, darwin-x64/arm64, windows-x64) on GitHub releases; keep the CLI free of native addons so compile stays clean; Node 25.5's --build-sea is a viable fallback if you want to stay on Node. (6) v2 consideration: for agents that can speak MCP, add Electric-style server-side edit tools (search_text returning relative-position-backed handles + targeted insert/replace) to avoid whole-file rewrites entirely.

RISKS:
  - Degenerate rewrite: if the agent rewrites most of the file, diff(base,new) approaches delete-all+insert-all — concurrent human edits inside rewritten regions are silently dropped and every Yjs relative-position anchor in those regions dies at once (Automerge documents this exact degradation for updateText; jupyter-collaboration's full-replace OOB path is an open bug tied to data loss). Without a change-ratio guard this will eventually destroy someone's work.
  - Silent fuzzy-patch misapplication: dmp patch_apply with Match_Threshold 0.5 can place a hunk in the wrong location on heavily-drifted text, or fail individual hunks; applyPatches returns a per-patch boolean array that MUST be checked and surfaced (reject/partial-conflict response), not ignored.
  - gc:false trap: if anyone implements 'reconstruct base from state vector' (or builds version history on Y.Snapshot), every document Y.Doc must run with GC disabled forever — unbounded growth inside Durable Objects, slower sync for every client. Pull metadata must not depend on this.
  - Atomicity of push: the merge (read current Y.Text → compute patch result → apply delta) must happen inside one DO execution/Yjs transaction; computing against a stale 'current' fetched over the network reintroduces the clobbering the design exists to prevent. The DO single-threaded model makes this easy — but only if the merge runs in the DO, not in a Worker in front of it.
  - Markdown-unaware merges: char-level dmp merges can interleave concurrent edits into syntactically broken markdown (split code fences, mangled tables) — Obsidian's auto-merge occasionally does this; snapshots/named versions are the necessary safety net, and a paragraph/line-level diff mode reduces it.
  - Large-file diff cost on Workers: char-level Myers diff on big documents is expensive (Loro warns >50k chars and offers update_by_line; dmp has line-mode); Workers CPU limits make a line-mode-first strategy advisable for big pushes.
  - Name collision: 'ink' is taken on npm (3.8M weekly downloads); also overloaded by Ink & Switch and inkle's ink language — branding/discoverability risk, scoped package required.
  - Auth flow choice: a Wrangler-style localhost-callback OAuth breaks for headless agents/containers (documented wrangler pain); shipping only that flow would block the primary persona. keytar is archived — don't bake it into a compiled binary.

AREA: anchoring
VERDICT: The layer holds up as designed — relative positions + stored TextQuoteSelector with Hypothesis-style fuzzy re-anchoring is the correct and proven architecture — with the caveat that anchor survival depends critically on (a) the DO never compacting/rebuilding Y.Doc history (which nulls every stored anchor at once) and (b) the server using a character-level minimal diff for CLI pushes, since any region the diff treats as delete+insert orphans all anchors within it.

RECOMMENDATION: Build the anchor record as a three-layer composite per comment/suggestion, stored in sidecar (D1/DO storage), never in the Y.Doc: (1) two Yjs relative positions — start created with assoc=0, end with assoc=-1 so boundary insertions fall outside — serialized via Y.encodeRelativePosition to base64 (or relativePositionToJSON); (2) a W3C-shaped TextQuoteSelector {exact, prefix: 32 chars, suffix: 32 chars}; (3) a TextPositionSelector {start, end} as a search hint. Resolution ladder (Hypothesis pattern, run server-side in the DO with followUndoneDeletions=false): resolve relative positions → if both resolve and the range is non-collapsed, verify current text against stored exact (cheap equality, then fuzzy); on failure or collapse, re-anchor by porting hypothesis/client's match-quote.ts (BSD-2-Clause, ~150 lines) onto approx-string-match v2 (MIT) over the plain markdown string — skip dom-anchor-text-quote entirely (unmaintained since 2017, DOM-coupled); on success re-mint fresh relative positions and refresh quote+position; otherwise mark orphaned. Run this pass synchronously after every CLI-push merge, and make the push merge use a character-level diff from @sanity/diff-match-patch (3.x, maintained; google/diff-match-patch is archived) to maximize anchor survival. RISKS:
  - Document compaction/rebuild is the single biggest hazard: any operation that recreates the Y.Doc from plain text (snapshot restore, storage migration, 'squash history' for size) makes store.getClock() fail for every stored anchor and nulls ALL comments/suggestions at once. The DO persistence design and the version-restore feature must either preserve update history or run a bulk quote-based re-anchor + re-mint positions as part of the operation.
  - Anchor survival after CLI push is a function of diff granularity, not of Yjs: a line- or paragraph-level diff turns small rewrites into delete+insert spans that orphan every anchor inside; a character-level diff (diff-match-patch family with semantic cleanup) preserves unchanged runs and their item IDs. The diff algorithm choice (owned by the sync/CLI layer) must be treated as part of the anchoring contract.
  - For agent-heavy workflows, quote-based re-anchoring will be the common path, not the exception — budget for it: run re-anchoring server-side in the DO right after each push merge, and refresh stored quotes/positions on every successful resolve so they don't go stale and degrade fuzzy-match quality over time.
  - Markdown is highly self-similar (repeated '```', '- ', '| --- |', duplicated headings), so exact quotes recur; prefix/suffix context and a position hint are mandatory, and short quotes (< ~8 chars) should be rejected or expanded at creation time. approx-string-match's maxErrors=len/2 ceiling can also produce false-positive re-anchors on short quotes — enforce a score threshold (~0.8 like Hypothesis) and treat low-score matches as orphans.
  - Accepting a suggestion after drift can splice garbage if validated by position alone: GitHub's precedent is to refuse to apply when target lines changed. Accept must re-resolve the anchor and verify the current range text against the suggestion's stored base text inside the same DO transaction that applies the edit.
  - Overleaf's ranges-tracker is AGPL-3.0 — use it as a design reference only; do not copy code into a proprietary codebase. Hypothesis client (BSD-2-Clause) and approx-string-match (MIT) are safe to port/vendor.
  - Yjs v14 attributions may obsolete a custom suggestion layer within a year (beta since late 2025, FOSDEM Feb 2026, government-funded). Keep suggestion accept/reject logic server-side and behind an interface so it can be swapped; conversely, do not wait for it — y-codemirror.next still targets v13 and v14 is not stable as of June 2026.
  - Relative positions resolved with default followUndoneDeletions=true give different answers to different clients after undo operations; the server must resolve with followUndoneDeletions=false for consistent shared anchors (yjs issue #638).
  - approx-string-match counts UTF-16 code units, so emoji/CJK-astral text inflates error counts and offsets; all stored offsets (TextPositionSelector, suggestion ranges) must consistently use UTF-16 code-unit indexing to match both Y.Text and CodeMirror conventions.
  - Rendering CriticMarkup found in files is contained, but anything beyond read-only rendering (round-tripping suggestions to CriticMarkup, editing through the markup) is demonstrably hard — Obsidian's Commentator is still beta with data-loss warnings after ~3 years.
